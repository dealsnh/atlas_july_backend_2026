# CLAUDE.md — Atlas Backend

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Atlas** is National Houses' internal lead-generation web app — a completely separate codebase from SiftStack (this company's other, older project), though both belong to the same company. **Never mix code, commits, or context between Atlas and SiftStack.** See the companion frontend repo, `atlas_july_frontend_2026`, for the React client.

Stack: Express + TypeScript, Postgres, JWT + API-key auth, per-state/county web scrapers feeding a shared `leads` table. Deployed on Railway (backend) / Vercel (frontend).

## Architecture

- **`src/scrapers/<state>.ts`** (e.g. `california.ts`, `missouri.ts`, `alabama.ts`) — one file per state, each exporting a `scrape<State>(county, fromDate, toDate, leadTypes?, scraperErrors?)` dispatcher that fans out to per-county-and-type scraper functions via a `runners: Record<string, () => Promise<Lead[]>>` map, run with `Promise.allSettled` and merged via `settleScraperResults()` (one source failing must never take down the others).
- **`src/scrapers/base.ts`** — shared `Lead` interface, `fetchWithRetry`, `fetchBlockedPage` (residential-proxy-aware fetch, see below), `fetchViaBrightDataWithSession` (cookie-jar-aware GET-then-POST for session-gated sites), `makeId`, `formatDate`, `settleScraperResults`.
- **`src/scrapers/assessor.ts`** — the shared, FREE county parcel-roll lookup (`lookupByAddress`, `lookupOwnerProperties`) used by nearly every scraper to resolve an owner name and mailing address from a bare situs address, or vice versa. This is the "no Enformion, no paid skip-trace service" foundation almost the whole California build rests on — always check whether a county already has a `ROLL_SPEC` entry here before reaching for anything else.
- **`src/config/county-lead-types.ts`** — the single source of truth for which lead types are actually LIVE per county (`COUNTY_DEFAULT_LEAD_TYPES`). **A type is listed only where a real scraper is wired for it.** Never add a type here speculatively.
- **Lead schema** (`base.ts`): `id, county, state, lead_type, owner_name, address, city, zip, mailing_address, mailing_city, mailing_state, mailing_zip, case_number, filing_date, assessed_value, tax_year, lender, loan_amount, sale_date, sale_amount, description, source_url, raw_data`. No first/last name split — `owner_name` is one string, so a source's own "LAST, FIRST" formatting can be passed straight through unmodified.

## Verify Before Building — the rule that has held up every time

**Never write scraper logic against an assumed data contract.** Every real scraper in this codebase was built only after independently confirming, with live requests, the exact response shape, required auth (or lack of it), and any server-side filtering — not from a reference doc's description, not from what a UI *looks like* it needs. See [[reference_finding_hidden_govt_apis]] (Claude's persistent memory) for the general technique playbook this project's whole Orange County build-out was found with. The short version:
- A "registration required" notice on a site often covers only ONE workflow (bidding, formatted export) — the underlying data API a site's own UI calls is frequently open with no login at all. Verify with one throwaway request before assuming a login is needed.
- An ArcGIS "Open Data Hub" page rarely shows the real `FeatureServer` URL directly — resolve the embedded item ID via `arcgis.com/sharing/rest/content/items/<id>?f=json`, and check for OTHER items in the same org (a "recent"/"view" layer is often a near-empty subset of a much better full layer).
- A layer's WMS/display name is not always its WFS-queryable feature-type name (GeoServer). A 400 "unknown type" error means check `GetCapabilities`, not give up.
- If a filter parameter (date range, status) is supposed to narrow results, prove it both ways — one query that should return nothing, one that should return a known match. A silently-ignored filter looks identical to a correctly-empty result otherwise.

## Orange County, CA — full build-out (complete as of 2026-09-12)

All six of the client's requested lead types are live: **Foreclosure, Code Violation, Tax Delinquent, Probate, Pre-Probate, Bankruptcy.** Water Shutoff was evaluated and formally eliminated (see below). All scrapers live in `src/scrapers/california.ts`.

### Bankruptcy
Central District of California bankruptcy court public RSS, matched to debtor names via the free county roll. The original, already-live scraper this whole build extended.

### Probate — `capublicnotice.com` (singular domain, NOT the plural `capublicnotices.com`)
Session-gated: a cold request to `/search/query` returns zero rows no matter how correct the parameters are — load the landing page first in the same session, then the query honors `firstDate`/`lastDate` exactly. Use `size=9000&page=0` (one oversized page; `page` doesn't actually paginate on this site, `size` does). Orange County is confirmed on each row via its own `location` field (a structural signal, not a text guess) plus the `30-YYYY-NNNNNNNN-PR-xx-CMC` OC Superior Court case-number pattern. Notices republish weekly under a fresh advert ID — dedupe on the case number. Truncated descriptions (~200 chars) still reliably carry the decedent name + case number before the cutoff, so no separate detail-page fetch is needed.

### Pre-Probate
Not a separate scraper — this is the SAME roll-derived "still on the tax roll as an estate" scan (`scanEstateOwners`/`scrapeRollDerived` in `roll-leads.ts`) already live for other states, just relabeled for California via `estateLeadType(state)`: California gets "Pre-Probate" (since real court-filed Probate already exists above, so this roll signal is the earlier/weaker stage) while every other state keeps "Probate" for the same underlying signal.

### Foreclosure — OC Clerk-Recorder (`cr.occlerkrecorder.gov`)
Nonjudicial-foreclosure state — CA forecloses through the Recorder, never a court docket, so this is the only real source. **Needs no browser/JS at all**, despite an earlier assumption (carried over from SiftStack's own research, which used a browser-automation tool this project doesn't have) that it did. The real contract, reverse-engineered from the site's own inline JS: a plain `GET` to establish an ASP.NET session cookie, then a plain `POST` to `Presentors/AjaxPresentor.aspx` reusing that cookie — `fetchViaBrightDataWithSession()` in `base.ts` implements this as a curl GET-then-POST pair sharing a cookie jar via `-c`/`-b`, routed through the same Bright Data residential proxy already used for MO/AL (this host needs it — direct connections from a non-residential IP time out entirely, a real network block, not a bot-fingerprint issue).

Grantor names on this site are indexed **`LAST FIRST [MIDDLE]`** — the opposite convention from a notice body — and mix the trustee company in with the actual owner in the same field, no role marker; both are handled the same way SiftStack's own `occa_foreclosure_address_resolve.py` already solved it (an entity-keyword list, not just the trailing "TR" suffix, since an individual owner can legitimately carry their own personal-trust "TR" too).

### Code Violation — no countywide feed exists; four of OC's 34 incorporated cities are live
Each city runs its own program. **Checked and confirmed dead ends (no free usable feed): Santa Ana, Huntington Beach, Costa Mesa, Fullerton (only a code-officer zone-boundary layer, zero case data), City of Orange.** 21 of the 34 cities have never been checked at all — more can be added the same way as these four, once found and verified.

- **Anaheim** — `services3.arcgis.com/.../CodeEnforcementCasesPublic/FeatureServer/0`, synced from Accela every 15 min, ~171k records. Owner name (`ownername`) AND address (`address`, format `"STREET\nCITY, ST ZIP"`) both come straight off the feed — no roll lookup needed to identify who to contact (roll is only used afterward to enrich/confirm the mailing address). Filter: `casestatus <> 'Closed'`.
- **Irvine** — `services2.arcgis.com/.../Code_Enforcement_Cases_AGO/FeatureServer/0`, ~34k records. Address only (`USER_FULL_ADDRESS`), **no owner name at all** — the free county roll is REQUIRED here, and a case with no roll match is skipped rather than uploaded nameless. Filter: `USER_Status <> 'Closed'`.
- **Newport Beach** — `nbgis.newportbeachca.gov/arcgis/rest/services/ArcGISOnlineDataGISViewer/FeatureServer/17`, ~20k records. Like Anaheim, owner name (`CASE_NAME`, "LAST, FIRST") and address (`ADDS`) both come off the feed directly. **This is the city's own ArcGIS Server, not ArcGIS Online's shared infra** — needs the residential proxy (`fetchBlockedPage`, `nbgis.newportbeachca.gov` is in `needsResidentialProxy()`) the same way the Recorder does, unlike Anaheim/Irvine. Filter: `STATUS NOT IN ('CLOSED','VOID')`.
- **Garden Grove** — a completely different, non-Esri stack (custom Leaflet portal backed by a real GeoServer WFS instance at `geonode.ggcity.org/geoserver/code/ows`, feature type `code:open_violations`). ~1,745 records. No owner name published — resolved via the roll, same as Irvine. The layer is server-side pre-filtered to open cases only (no separate "closed" layer exists to exclude). Server-side date filtering via GeoServer's `CQL_FILTER` on `opened_on` — confirmed to genuinely apply (tested both an empty-result window and a known-match window). `opened_on` is already a clean `YYYY-MM-DD` string. **Found via the portal's `<gg-map-portal config="./config.yml">` web component's own config attribute** after a headless render came back nearly empty (the component never initializes in a scripted context at all — confirmed zero JS errors, it just silently never runs). A `code:red_tagged_cases` layer also exists (17 condemned/uninhabitable-property records, a strong distress signal) — found but not wired in, a candidate for a future addition.

### Tax Delinquent — `bid4assets.com`'s Orange County tax-defaulted property auction storefront
**No login/registration needed at all to READ listings or detail pages** — the site's documented registration gate is only for the deposit/bidding flow. The county's auction schedule is genuinely **irregular** (no fixed calendar — recent ones were June and Sept 2025), so this is the one CA scraper that deliberately does NOT filter by the passed `fromDate`/`toDate` window; it just reports whatever's currently posted and still open. An already-closed auction, or nothing currently posted, both correctly produce zero leads — not an error.

Contract (reverse-engineered from the page's own inline Kendo grid config): `GET /Orange` → parse the current `StorefrontId` (a hidden input) + auction collection group IDs (embedded folder-list JSON) → `POST /api/storefront/auctions/index` per group for the item list (APN-bearing title, min bid, close time — **no address at this level**) → `GET /auction/index/{auctionID}` for the actual "Item Specifics - Parcel Information" table (APN, legal description, full address). No owner name anywhere — resolved via the free county roll, same as Irvine/Garden Grove. Items marked with a `"***Withdrawn***"` title prefix (paid off / pulled from sale) are excluded via a text match, since there's no documented status-code enum to rely on instead. `bidCloseTime` arrives as a bare no-timezone datetime string — handled via a direct string-prefix compare, not a `Date` round trip (see the date-parsing gotcha below).

### Water Shutoff — eliminated from the roadmap, not merely deferred
California's SB 998 only requires water utilities to report an **annual aggregate count** of residential disconnections, never a list of addresses. Confirmed twice: the specific state dataset the client pointed to turned out to be about water production/delivery *volume*, not disconnections at all, and a direct search of `data.ca.gov` for "SB 998"/"shutoff"/"disconnection" turned up nothing relevant. Even a hypothetically-perfect SB 998 source would never produce individual per-property leads — it's a statistic, not a list. Do not resurrect this without a fundamentally different kind of source (e.g. a individual utility's own per-property records, which no utility publishes).

## General gotchas that will resurface on the next state/county expansion

**Bare datetime strings with no timezone marker will silently shift a date by one day on this workstation.** The local machine's timezone sits AHEAD of UTC, so any `new Date(bareString).toISOString()` round-trip pushes the date forward into the next day. Hit this in the Probate scraper (notice `datetime` had no zone marker) and the Foreclosure scraper (`formatDate()`'s round trip) before the fix pattern was established: for anything needing day-level accuracy, extract the date via direct string slicing (`value.split("T")[0]`), never via a `Date` object. **Epoch-millisecond integers are NOT the same risk** — they're an absolute instant with no parsing ambiguity, so `new Date(ms).toISOString().split("T")[0]` is always safe for ArcGIS's date fields specifically.

**The residential-proxy list (`needsResidentialProxy()` in `base.ts`) is a manually-maintained hostname allowlist, not automatic.** A new source hosted on a city's own ArcGIS Server (as opposed to ArcGIS Online's shared `*.arcgis.com` domains) may need adding here — test with a plain `fetchWithRetry` first; if it times out/connection-refuses (not a 403/bot-challenge), that's the signature of this specific block, and the fix is adding the hostname here plus using `fetchBlockedPage()` instead of a raw fetch.

**Squash-merging a PR, then merging a second PR that was branched off the first (not `main`), breaks the stack.** See [[feedback_atlas_workflow_rules]] (Claude's persistent memory) for the exact fix (`git rebase origin/main` + force-push + repoint the PR base). Simplest prevention: branch new work off `main` after the prior PR is actually merged, rather than stacking a branch on another still-open one, unless there's a specific reason to.

**Local test runs need a real Postgres** (`npx vitest run` — the test suite spins up the actual app against `TEST_DATABASE_URL`). No SQLite/mock DB fallback exists. `postgresql://postgres:postgres@localhost:5432/atlas_test` against a local PostgreSQL 16 install is what this project has used.

## Security fixes shipped (verify these stay fixed on any future refactor of these files)

- **`GET /api/v1/leads` and `/leads/export` had NO auth at all**, unlike every other route in `leads.routes.ts` — anyone with the URL could pull the entire leads database (names, addresses, skip-traced phones/emails) with zero credentials. Fixed by adding the same `authMiddleware` guard already used elsewhere in that file. If a future route addition in this file doesn't have `asyncHandler(authMiddleware)`, that's very likely a bug, not a deliberate public route.
- **Login/signup brute-force protection** — rate limiter keyed on IP+email (10/15min login, 10/hour signup). Scoped: does not stop a fully distributed attack (many IPs, one email) — that would need a DB-backed per-account counter, not yet built.
- A shared test fixture (`test-lead-001`) was silently failing to persist because `insertLeadIfNotExists()`'s save gate (`isLeadSaveable()`) requires owner name + street address + **mailing** address, all three, or the row is dropped with no error. If a test starts failing "record not found" against a fixture that looks correct, check it has all three fields, not just the ones that look obviously required.
